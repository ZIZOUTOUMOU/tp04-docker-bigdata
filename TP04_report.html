0. Project overview

The application containerized in this TP is the analysis of TP03 rewritten as a Python script. It processes the full Kaggle dataset eCommerce behavior data from multi-category store (files 2019-Oct.csv, 5.7 GB, and 2019-Nov.csv, 9.0 GB) and reproduces the TP03 cleaning steps and measures: total events, unique users, purchases, revenue, conversion rate, events by type, top 10 brands by revenue, revenue by main category and purchases per hour.

The CSV files are far too large to fit in memory with a plain pd.read_csv, so the script reads them in chunks of 1 million rows and keeps only running totals. The files are never copied into the image: they are mounted read-only at run time (-v ./data:/app/data:ro), and .dockerignore keeps the 14 GB out of the build context. The file to analyse is chosen with the environment variable DATA_FILE, so the same image processes October or November.

3. Task 3 – Containers

Three containers were created from the pulled image and connected to a user-defined network.

docker network create bigdata-net
docker network ls

docker run -d --name analysis1 --network bigdata-net -p 8081:80 -v "${PWD}/data:/app/data:ro" zizoutoumou/tp04-analysis:v1 sleep infinity
docker run -d --name analysis2 --network bigdata-net -p 8082:80 -v "${PWD}/data:/app/data:ro" zizoutoumou/tp04-analysis:v1 sleep infinity
docker run -d --name analysis3 --network bigdata-net -p 8083:80 -v "${PWD}/data:/app/data:ro" zizoutoumou/tp04-analysis:v1 sleep infinity

docker ps
docker network inspect bigdata-net
  • docker network create bigdata-net creates a private bridge network. Containers attached to it can reach each other by name.
  • -d runs the container in the background, --name fixes its name, --network attaches it to bigdata-net.
  • -p 8081:80 maps port 8081 of the host to port 80 of the container (8082 and 8083 for the other two). The application is a batch job and does not listen on a port, so the mapping only demonstrates the syntax requested by the TP.
  • -v ...:ro mounts the data folder read-only.
  • sleep infinity replaces the default CMD. The analysis script exits when it finishes, and an exited container is not “running”; this command keeps the three containers alive so they can be verified, and the analysis is then started inside them with docker exec.

4. Task 4 – Run the application with Docker Compose

compose.yaml (the file of the TP, with two additions: the image name and the DATA_FILE variable so Compose processes the full November file):

services:
  data-analysis:
    build: .
    image: zizoutoumou/tp04-analysis:v1
    container_name: tp04-analysis
    environment:
      - DATA_FILE=2019-Nov.csv
    volumes:
      - ./data:/app/data:ro
    restart: "no"
docker compose up --build
docker compose ps -a
docker compose down
  • docker compose up --build builds the image (all layers were cached), creates the network tp4_default and the container tp04-analysis, runs the analysis and exits with code 0.
  • docker compose ps -a lists the container of the project. The option -a is needed to also see a container that has already stopped.
  • docker compose down removes the container and the network created by Compose.

Questions

What problem does Docker Compose solve?

A real environment is often made of several containers (an application, a database, a message broker…), each needing a long docker run command with its image, network, ports, volumes and environment variables. Typing, remembering and sharing these commands is error-prone. Docker Compose describes the whole environment declaratively in one YAML file and starts, stops and removes it with a single command. The file is versioned with the code, so the environment is reproducible on any machine. Compose also creates a shared network automatically, so the services reach each other by service name.

Compare docker run with docker compose up.

docker rundocker compose up
ScopeOne containerAll the services of a project
ConfigurationCommand-line options, typed each timeWritten once in compose.yaml
ImageMust exist already (built or pulled before)Can build it with build: / --build
NetworkCreated manually (docker network create)Created automatically (tp4_default)
ReproducibilityDepends on the command that was typedSame file gives the same environment
Cleanupdocker stop / docker rm for each containerdocker compose down removes everything

In this TP, Task 3 needed three long docker run commands plus a manual network, while Task 4 needed one file and three short commands. Compose uses the same engine and the same images; it is a more convenient way to drive them.

How could you extend the Compose project to include a database service?

Add a second service (for example PostgreSQL) to compose.yaml, give it a named volume so the data survives docker compose down, and make the analysis service wait for it. Both services share the default network, so the application connects using the service name db as hostname:

services:
  db:
    image: postgres:16
    container_name: tp04-db
    environment:
      POSTGRES_USER: bigdata
      POSTGRES_PASSWORD: bigdata
      POSTGRES_DB: ecommerce
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U bigdata -d ecommerce"]
      interval: 5s
      retries: 10

  data-analysis:
    build: .
    container_name: tp04-analysis
    environment:
      - DATA_FILE=2019-Nov.csv
      - DB_HOST=db
      - DB_NAME=ecommerce
      - DB_USER=bigdata
      - DB_PASSWORD=bigdata
    volumes:
      - ./data:/app/data:ro
    depends_on:
      db:
        condition: service_healthy
    restart: "no"

volumes:
  pgdata:

The Python script would then write its results (KPIs, revenue per brand, purchases per hour) into tables with a driver such as psycopg2 or SQLAlchemy (added to requirements.txt), instead of only printing them. In a real project the password would be kept in an .env file rather than in the YAML. The same pattern works for MongoDB, MySQL or any other database image.

5. Task 5 – Report summary

What is Docker, and why is it useful in data-science projects?

Docker is a platform that packages an application together with everything it needs to run (operating-system libraries, language runtime, dependencies, configuration) into a standard unit called a container. Containers share the kernel of the host, so they are much lighter and faster to start than virtual machines.

It is useful in data-science and big-data projects because:

  • Reproducibility: the environment is fixed by the Dockerfile (Python 3.11, pandas 2.2.3), so the analysis gives the same results on any machine. In this TP, two runs of November gave identical numbers.
  • Portability: the image was pushed to Docker Hub and pulled again; anyone can run it with one command, without installing Python or pandas.
  • Isolation: dependencies of different projects do not conflict.
  • Separation of code and data: the 14 GB of CSV files stay outside the image and are mounted read-only, and the same image processed both October and November.
  • Scalability and orchestration: several containers can run in parallel (three containers on one network in Task 3) and be described as a whole with Compose, which prepares the ground for tools such as Spark clusters, databases and Kubernetes.

Explain the difference between a Docker image and a container.

A image is a read-only template made of stacked layers: it contains the files, libraries and the default command, but it does not run. It is built from a Dockerfile and can be stored in a registry such as Docker Hub (zizoutoumou/tp04-analysis:v1, 417 MB on disk, 90 MB compressed).

A container is a running (or stopped) instance of an image: Docker adds a thin writable layer on top of the image, gives it a process, a network and volumes, and starts it. Many containers can be created from one image; in Task 3, analysis1, analysis2 and analysis3 all come from the same image. Deleting a container does not delete the image. An analogy: the image is the class (or the recipe), the container is the object (or the dish).

Explain the purpose of FROM, WORKDIR, COPY, RUN and CMD in the Dockerfile.

InstructionPurposeIn this TP
FROMSets the base image on which the new image is built; it is always the first instruction.FROM python:3.11-slim: a small Debian image with Python 3.11 already installed.
WORKDIRSets the working directory inside the image (creates it if needed) for the following instructions and for the running container.WORKDIR /app
COPYCopies files from the build context (my machine) into the image.COPY requirements.txt . then COPY app.py .
RUNExecutes a command at build time and saves the result as a new layer (installing packages, for example).RUN pip install --no-cache-dir -r requirements.txt
CMDDefines the default command executed when a container starts. It is not run during the build and can be overridden at docker run.CMD ["python", "app.py"]; overridden with sleep infinity in Task 3.

requirements.txt is copied and installed before app.py on purpose: Docker caches each layer, so when only app.py changes, the slow pip install layer is reused. This is why the rebuild done by Compose took under 2 seconds.

6. Limitations and notes

  • Duplicate rows are removed inside each chunk (1 or 2 million rows), not across the whole file, because a global drop_duplicates would need all rows in memory. The effect on the totals is expected to be very small.
  • Large numbers appear in scientific notation in the console (for example 1.275125e+08 = 127,512,500); this is only a display format.
  • The hourly breakdown uses the UTC timestamps of the dataset.
  • Compose retagged zizoutoumou/tp04-analysis:v1 locally with a fresh build (same layers, new manifest). The image on Docker Hub was not modified.
  • The raw CSV files are not in the repository because of their size (14 GB). They can be downloaded from Kaggle: eCommerce behavior data from multi-category store (mkechinov) and placed in data/.
